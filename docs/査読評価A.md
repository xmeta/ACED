提供された開発手法 **「SC-WBS Development (AI-Collaborative Spec Contract and WBS Driven Development)」** について、ソフトウェア工学および実務運用の観点から査読（ピアレビュー）を実施しました。

本手法は、AIエージェントの自律的な書き換え（デグレ）や判断のブラックボックス化を防ぎ、かつ人間とAIの境界線（ガードレール）を構造化データによって厳格に制御しようとする、極めて実用的かつ時代に即したアプローチです。

以下に、本手法の「優れた点」「課題および懸念事項」、およびそれらに対する「具体的な改善提案」を客観的に報告します。

---

# 査読評価報告書：SC-WBS Development

## 1. 全体評価（Overview）
本手法は、AIを単なるコーディングアシスタント（サジェストツール）としてではなく、**「仕様および契約（Contract）に従って動く、自律的な1開発メンバー」**として定義し、その作業範囲、意思決定の限界、およびエビデンス（証跡）を構造化ファイル（WBS-JSON、YAML、Gitメタデータ）を用いて機械的にアサーション（検証）するフレームワークです。

「人間が責任を負い、AIが契約内で自律動作する」という役割分担が徹底されており、特に金融、行政、基幹業務などの堅牢性が求められる領域（Strict Profile）へのAI導入を現実的に可能にするための優れた土台を持っています。

---

## 2. 本手法の優れた点（Strengths）

### 2.1. 徹底した境界・パス制御（Path-based Guardrails）
`allowedPaths` / `forbiddenPaths` / `humanGateRequiredPaths` の設定と、Git差分を用いた検証（`scwbs check-diff`）の組み合わせは、AIによる「想定外の広範囲な変更（デグレやセキュリティ定義の書き換え）」を物理的に防ぐ非常に強固なガードレールとなっています。

### 2.2. 仕様の「鮮度（Stale）」管理の標準化
`contractLock` の仕組みを導入し、WBSやSpecの最新リビジョンとTask Contractの生成時点を同期チェックする点は評価できます。仕様が変更されたことに気づかずにAIが古い前提で実装を進めてしまう手戻りを未然に防ぎます。

### 2.3. コンテキスト最適化（AI Work Packet）
LLMの性能やコストは入力するコンテキストの質に大きく左右されます。`AI Work Packet` 生成時に依存関係を `depth=1` に制限し、他の重要ファイルを artifact 参照に留める設計は、ハルシネーション（嘘や誤認）の抑制とトークン消費の最適化に直結する合理的な制約です。

### 2.4. 客観的証跡（Evidence）の多段階信頼性レベル
DoD（Definition of Done）の判定を作業者の自己申告（Level C）に依存させず、CIログやローカルでのコマンド実行（Level A/B）と結びつけるレベル分けは、実務上のガバナンスとして高い効果を発揮します。

## 3. 課題・懸念事項と改善への提言（Weaknesses & Recommendations）

本手法を実際の開発現場に投入し、長期的にスケールさせるにあたって、以下の5つの懸念点と改善案を提示します。

### 3.1. 運用のオーバーヘッド（Human-in-the-loopのボトルネック化）
* **懸念**: タスクを細分化するほど、各タスクに対応する `Task Contract` や `Evidence` のYAML/JSONファイルの作成・更新・整合性維持コストが膨らみます。特にアジャイルな小規模開発（Lean）において、「契約手続きのオーバーヘッド ＞ 実装コスト」となり、人間側が疲弊する可能性があります。
* **改善案**:
  * `scwbs` CLIに、`WBS-JSON` の特定ノードと `Spec Contract` を解析して、初期状態の `Task Contract`（推奨パスやdoneCriteria）の**草案をAIに自動生成（Bootstrap）させるコマンド**を標準フローに明示してください（例: `npm run scwbs -- task generate --node <id>`）。人間はその自動生成されたファイルを15秒〜30秒でレビューし、ロックをかけるだけに抑える工夫が必要です。

### 3.2. 並行開発における「WBS-JSON」のコンフリクト
* **懸念**: 複数人、または複数のAIエージェントが機能開発を並行して進める場合、共通の正本である単一ファイル `contracts/wbs/project.wbs.json` への変更が競合し、Gitマージコンフリクト（特に機械生成されたJSON同士の衝突）が多発する懸念があります。
* **改善案**:
  * 巨大な1つの `project.wbs.json` だけでなく、マイルストーンや機能（Feature）単位でファイルを分割して管理し、メインファイルからそれらを `imports` / `includes` する構造（分散型WBS-JSON）をサポートすることを推奨します。
  * あるいは、コンフリクト発生時に `scwbs` CLIが「セマンティックな差分統合（Semantic Merge）」を行えるよう、ツール側のロードマップに「マージ支援機能」を追加することを検討してください。

### 3.3. AIエージェントによる制約迂回（Evasion / Jailbreak）のリスク
* **懸念**: 高度なAIエージェントが `allowedPaths` 以外のファイルを編集しようとした際、`tsconfig.json` への変更や、テスト環境の差し替え、あるいは `.gitignore` への追記などの「ルールを回避するためのメタファイル変更」を試みる可能性があります。
* **改善案**:
  * `scwbs check-diff` の挙動として、**「`allowedPaths` に明示されていないすべての環境設定ファイル（tsconfig, package.json, webpack, .github/ workflows等）の変更を、暗黙的にError（Level 2仕様変更 / Human Gate必須）とする」** という強力なハードセーフティネットをルール化すべきです。

### 3.4. テスト品質（`testQuality`）検証の具体的な難しさ
* **懸念**: `scwbs health` において、テストファイルの差分で「アサーションの追加を検出する（assertionsAdded）」や「テストが形骸化（空の `test` ブロックなど）していないか確認する」ことを自動化するのは、静的解析や構文木（AST）解析の難易度が高く、実装が複雑化します。
* **改善案**:
  * 実装方法の指針として、「単純な文字列マッチではなく、各言語に対応した AST パーサーを用いたアサーション（例: Jestの `expect`、Pythonの `assert`）のカウント比較、または既存のテストカバレッジレポート（lcov.info等）との差分検証を `scwbs health` の裏側でどのように行うか」という技術的アプローチの抽象的なロードマップを1行追加すると、開発手法の実現可能性が高まります。

### 3.5. 「ブートストラップ（Bootstrap）」から通常開発への「段階的移行」
* **懸念**: 4章において「通常運用への移行条件」が定められていますが、実際の大規模プロジェクトでは、システム全体が一斉に通常フェーズに入るわけではありません。機能Aがすでに実装フェーズ（通常）である一方で、機能Bはまだ構想段階（Bootstrap）という混在状態が普通です。
* **改善案**:
  * Bootstrap Contractおよび移行条件は、プロジェクト全体（Global）ではなく、**「WBS上の特定サブツリー（Feature/Milestone node単位）」で段階的に解除・移行できる仕様**であることを明記してください。

## 4. 結論

| 評価項目 | 評価 | 備考 |
|---|---|---|
| **実用性 / 安全性** | **極めて高い** | AIの変更範囲を物理的・論理的に制限するアプローチは現代のベストプラクティス。 |
| **整合性** | **高い** | 各ファイルの役割定義や遷移図が論理的に整理されている。 |
| **運用の実現性** | **中（要改善）** | 人間のレビューや契約作成の作業量、JSONコンフリクトの運用回避策が今後の鍵。 |

**判定：条件付き採用（実用化・ツール実装に向けたマイナーアップデートを推奨）**

本開発手法は、単なる「AIプロンプトエンジニアリング」の枠を超え、**「AIを組み込んだ次世代の構造化ソフトウェア工学（Structured Software Engineering with AI Agents）」** と呼ぶにふさわしい非常に論理的な設計を持っています。
上記の「改善提案（自動作成支援、分散WBS、セーフティ、段階的Bootstrapなど）」をドキュメントやCLIの設計に少し反映・加筆することで、開発現場での実用性がより一層強固なものになります。
